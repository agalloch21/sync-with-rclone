# sync-with-rclone 产品需求文档

## 1. 产品定义

`sync-with-rclone` 是一个面向“项目文件夹”的桌面同步工具。

它的目标不是提供通用文件同步，而是解决这样的问题：

**一个本地项目目录里同时包含代码、设计稿、文档、素材、测试仓库和临时内容，用户希望把它整体同步到 NAS，但又不希望把大量无意义文件一起同步。**

本项目的核心价值是：

- 支持本地 `.gitignore` 风格过滤
- 同步前展示差异
- 允许用户勾选后再执行
- 面向项目目录而不是面向普通文件夹同步

## 2. 背景问题

典型现状如下：

- 普通文件可以直接用 NAS 或网盘工具同步
- 正式代码仓库通常用 Git 管理，不适合完全依赖 NAS 同步
- 非正式仓库、测试仓库、实验项目仍然需要长期保存在项目目录里
- 这些目录里经常有 `node_modules`、构建产物、缓存、临时文件，不适合直接同步到远端

因此，用户需要的不是“再一个同步工具”，而是：

**一个理解项目目录结构，并能尊重 `.gitignore` 思维方式的同步工具。**

## 3. 目标用户

目标用户主要是：

- 同时管理代码、设计、文档、资产的个人创作者或独立开发者
- 把 NAS 当作项目主存档位置的人
- 有多个设备，需要在不同机器间恢复项目目录的人
- 有很多非正式仓库或临时项目，但又希望统一归档的人

## 4. 第一阶段目标

第一阶段只聚焦一条最小可用闭环：

1. 用户从系统右键菜单发起 `Push` 或 `Pull`
2. 程序获取本地路径和动作类型
3. 程序扫描本地与远端目录
4. 程序计算差异
5. 程序弹出窗口展示差异树
6. 用户勾选需要同步的内容
7. 用户确认后程序继续执行同步
8. 程序展示结果摘要

CLI 路径下也应遵守同样原则：

1. 先展示差异摘要和树
2. 用户确认后才继续执行

## 5. 非目标

第一阶段明确不做：

- 实时双向同步
- 常驻后台监听
- 自动冲突合并
- 文件内容级 diff 编辑器
- 高级文件系统元数据同步
- 远端 ignore 规则处理
- 团队协同和权限系统

## 6. 核心功能

### 6.1 `Push`

- 从当前本地文件夹推送到对应 remote 路径
- 程序先根据 config 判断当前本地文件夹属于哪个同步任务
- 若属于某个同步任务，则根据该任务中的相对路径推导对应 remote 路径
- 本地扫描时应用 ignore 规则
- 执行前展示差异树

### 6.2 `Pull`

- 从对应 remote 路径拉取到当前本地文件夹
- 程序先根据 config 判断当前本地文件夹属于哪个同步任务
- 若属于某个同步任务，则自动推导默认 remote 来源路径
- 执行前展示差异树

### 6.3 `Push To...`

- 程序先根据 config 判断当前本地文件夹属于哪个同步任务
- 若属于某个同步任务，则展示该同步任务对应 remote 根目录下的目录树供用户选择目标目录
- 选择范围必须限制在该同步任务内部，不允许跨任务同步
- 后续逻辑与 `Push` 一致

### 6.4 `Pull From...`

- 程序先根据 config 判断当前本地文件夹属于哪个同步任务
- 若属于某个同步任务，则展示该同步任务对应 remote 根目录下的目录树供用户选择来源目录
- 选择范围必须限制在该同步任务内部，不允许跨任务同步
- 后续逻辑与 `Pull` 一致

### 6.5 配置驱动的同步任务

配置中需要支持：

- 多个同步任务
- 一个本地根目录对应一个 remote 根目录
- 每个同步任务只绑定一个 `rcloneRemote` 和一个 `remoteBasePath`
- 每个任务可附加额外 `.gitignore` patterns
- 路径匹配和相对路径推导
- `Push To / Pull From` 的任务内目录选择
- 禁止跨任务同步

目标是让用户在常见 `Push / Pull` 场景里，不需要每次重新选择目标目录。

### 6.6 安装后可直接从右键菜单触发

- Windows 安装包需要注册目录级右键菜单
- 右键菜单触发后，程序应直接拿到动作类型和当前目录路径
- 用户不需要先手动打开应用，再去选择目录
- 卸载时应移除这些菜单项

### 6.7 第一阶段配置方式

- 第一阶段暂不实现图形化配置管理页
- 用户需要手动编辑配置文件来建立 `syncJob`
- 用户需要手动编辑 `rclone` 配置来准备 remote
- 右键菜单是第一阶段的正式主入口
- 直接双击桌面可执行文件不作为第一阶段主要使用方式

## 7. 核心产品原则

### 原则 1：先确认，再同步

用户必须先看到差异，再决定同步哪些内容。

### 原则 2：本地过滤优先

本地 `.gitignore` 风格过滤是产品核心能力，不是可有可无的附加功能。

### 原则 3：先保守，再自动化

第一阶段优先保证可理解、可控、可回退，不追求“全自动”。

### 原则 4：删除操作必须谨慎

所有可能导致删除的同步行为都需要明显提示。
